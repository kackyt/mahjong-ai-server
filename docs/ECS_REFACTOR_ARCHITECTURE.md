# ECSリファクタリング：設計方針とアーキテクチャ

本ドキュメントは、麻雀エンジンを「AI Ready（AIが容易に拡張・修正可能）」なECS（Entity Component System）アーキテクチャへ移行するための設計指針を定義する。

## 1. 設計理念

現状の「FlatBuffersのデータ構造にロジックが密結合している」状態を解消し、「内部ロジック（ECS）」と「外部インターフェース（FlatBuffers/DLL）」を完全に分離する。

- **Logical Layer (ECS)**: 牌、プレイヤー、河、ルールなどの「真の状態」をEntity/Componentとして管理。ロジックは副作用のないSystemとして記述。
- **Interface Layer (Mapping)**: DLLやUIに対し、その都度必要な情報をECSから切り出し、期待される形式（FlatBuffers等）に変換して提供。

## 2. 厳格なメモリ管理とDLL分離

DLLインターフェースとの互換性を維持しつつ、安全性を担保するための鉄則を定める。

### 2.1. 物理的なメモリ分離
- **システム（ECS）側**: プロセス内のヒープ領域で動的にコンポーネントを管理。
- **DLL側**: 自身が確保したメモリ領域（`inst`）にのみアクセス。
- **データ授受**: DLLはシステム側のメモリを直接参照してはならない。システムが提供するコールバック関数を介した「コピー（書き込み）」のみで情報の授受を行う。

### 2.2. レジストリ（Context Lookup）方式
グローバルな `static mut` ステートへの依存を排除し、マルチ対局（Instance-based）をサポートする。
- DLLからのコールバック時に渡される `inst` ポインタ（DLLのプライベートメモリ領域へのポインタ）を「検索キー」として利用する。
- システム内部に、`inst` ポインタと、対応する `ECS World` を紐付ける「非公開レジストリ（HashMap等）」を保持する。
- これにより、DLLに内部ポインタを漏らすことなく、正しい対局データへのアクセスを実現する。

## 3. 計算ロジック（アルゴリズム）の共通化

点数計算やシャンテン数判定など、麻雀の核心となるロジックの管理。

- **Value Level（ID非依存）**: アルゴリズムは、EntityのIDを一切関知せず、牌の種類と数（`PaiState` 等）の「計数値」を入力とする純粋関数として実装する。
- **Entity Level（ID管理）**: 山牌の追跡や特定の牌の移動は、ECSシステムがID（0-135）で管理。計算時にはIDを「種類」に変換してアルゴリズムに渡す。
- **メリット**: 同一の計算クレートを、システム側の「本番実行」とDLL側の「シミュレーション」の両方で共有でき、論理的な一貫性が100%保証される。

## 4. AI Ready な開発フローへの転換

AIコーディングアシスタントが副作用を最小限に抑え、安全にロジックを拡張できる状態を目指す。

- **局所化された副作用**: 「打牌」や「鳴き」の処理を、特定のSystemクラス（または関数）に完結させる。他のSystemを壊すことなく、特定のルール分岐を追加可能にする。
- **ガードレールの提供**: 「状態を直接書き換える」代わりに、「コンポーネントを追加/削除する」というECSのパターンを強制することで、複雑な状態遷移バグを抑制する。

## 5. 実装ロードマップ（想定）

1. **ECSエンジンの導入**: `hecs` 等の軽量ECSライブラリの導入。
2. **コンポーネントの定義**: `Hand`, `Discard`, `Score`, `Wind` などの定義。
3. **コールバックの再実装**: `interface.rs` の内部を「G_STATE参照」から「Registry検索 ＆ Worldクエリ」に差し替え。
4. **ロジックの移譲**: 既存の `multi_replace_file_content` などの巨大ロジックを、独立したSystemへ段階的に切り出し。
